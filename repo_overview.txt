HANGMAN.AI REPOSITORY OVERVIEW
==============================

Purpose
-------
This document is a source-based inventory and architecture handoff for an
external audit. It describes the files found in the working directory and the
behavior visible in the source; it is not itself a security assessment.

The application is a browser-based word-guessing game built with React and
Vite. It combines Wordle-like full-word guesses and per-letter color feedback
with a Hangman-themed character, progressive levels, and AI-generated hints
and dialogue. The current AI integration is OpenRouter (not the Groq provider
mentioned in older project text).

Quick facts
-----------
- Frontend: React 18, React Router, Vite, Tailwind CSS, and regular CSS plus
  JavaScript inline styles.
- Game engine: client-side JavaScript class backed by a bundled JSON word list.
- AI calls: OpenRouter chat completions, optionally via a small Node HTTP proxy.
- Persistence: no game/session persistence is implemented in the active hook.
- Automated tests: package.json defines no test or lint command. The proxy
  script is a manual live-request check, not an automated test suite.
- npm commands: `npm run dev`, `npm run build`, `npm run preview`, and
  `npm run proxy`.
- Vite development server defaults to port 3000. The standalone proxy defaults
  to port 4000.

Startup and request flow
------------------------
1. Vite serves index.html, which mounts src/main.jsx. main.jsx imports global
   CSS and renders App inside React.StrictMode.
2. App.jsx maps `/`, `/game`, `/how-to-play`, and `/credits` to page components.
3. Game.jsx calls useWordle(). The hook creates a Wordle instance; Wordle picks
   a word from dictionary.json through wordSelector.js.
4. A submitted full-word guess passes from GuessInput through useWordle to
   Wordle.submitGuess(). The engine validates it, records it, computes
   green/yellow/gray feedback, and determines win/loss.
5. Game.jsx displays state using the game board, status, and Hangman
   components. Incorrect guesses advance the visual character.
6. A hint request builds context in hintService.js, then aiService.js sends a
   chat-completions request through openrouterClient.js. Dialogue requests
   follow a similar path through dialogueService.js.
7. In development, openrouterClient.js selects the relative path
   `/api/openrouter`; server.js exposes that endpoint on port 4000. vite.config.js
   does not currently define a proxy from port 3000 to port 4000, so the
   development integration requires an additional forwarding arrangement or
   configuration for the relative frontend request to reach server.js.

src/game/
-----------

src/game/wordle.js
  Wordle class, the core game engine. Constructor selects a word for the level
  and stores its definition, difficulty, length, guesses, and status.
  `isValidGuess()` normalizes and checks length, A-Z characters, and duplicate
  guesses. `submitGuess()` records valid guesses, generates per-position
  feedback, and updates win/loss status using level attempt settings.
  `generateFeedback()` marks exact-position matches first, then misplaced
  letters without reusing already matched answer positions. `getState()`
  returns the current game state; `reset()` selects a new word at the same
  level; `nextLevel()` increments level and resets; `getHintData()` prepares
  answer and progress data for hint context creation. This engine runs in the
  browser and `getState()` includes the answer word.

src/game/wordList.js
  Legacy large static `WORD_LISTS.easy` array and `getRandomWord()` helper.
  The active game engine imports wordSelector.js instead; this file is not
  part of the active word-selection path.

src/game/wordSelector.js
  Imports dictionary.json, maps level numbers to word-length/difficulty
  filters, selects a random matching candidate, and returns its word and
  metadata. `getWordsForLevel()` returns a reduced list for testing/admin use;
  `getDifficultyInfo()` reports filtering information. There is no tracking to
  prevent repeats. For out-of-range levels it uses a broad fallback filter,
  while game attempt settings separately fall back to level 1 in wordle.js.

Runtime behavior, state, and data contracts
============================================

Application routes and page responsibilities
---------------------------------------------
- `/` renders Home. Navigation buttons use React Router's useNavigate() to
  reach the game, instructions, or credits.
- `/game` renders Game. Game initializes one game session at level 1 when the
  page component mounts. It does not restore a previous game from storage.
- `/how-to-play` renders static instructions and a navigation action to start
  the game.
- `/credits` renders static credits/technology/feature copy and navigation.
- App.jsx has no explicit catch-all route for unknown paths; the router renders
  no matching page content for an unknown URL.
- Route-level pages are exported as named exports from their page modules.
  App.jsx is the default export and owns route registration.

Game state lifecycle
--------------------
1. `useWordle(1)` constructs a `Wordle` instance and snapshots `game.getState()`
   into React state. A selected answer is therefore fixed for that instance.
2. State includes the secret word, definition, numeric difficulty, word length,
   submitted guesses, status, level, attempts used/allowed, and game-over flag.
   The hook additionally tracks per-guess feedback, a status message, hints
   used, last hint timestamp, chat visibility, chat messages, and loading state.
3. GuessInput accepts a complete A-Z word of exactly the selected word length.
   On submit, Game's handler delegates to the hook, which calls the mutable
   Wordle instance. Valid guesses update the engine and then cause React state
   and feedback history to be refreshed.
4. An invalid guess is not recorded in the engine. Its validation message is
   returned to the hook and stored as the page status message; GuessInput's own
   local error is reserved for its length check. Valid but incorrect guesses
   consume an attempt and add a feedback row.
5. A correct guess sets the engine status to win. Reaching the configured
   attempt count on an incorrect guess sets it to lose. Game then renders a
   Next Level button for wins or Try Again for losses.
6. Next Level increments the numeric level and selects a new random word;
   Try Again selects a different random word at the same level. Both reset
   guesses, status, feedback, hint usage, and chat messages. They do not
   preserve/replay the previous answer or attempt history.
7. Leaving and re-entering `/game` mounts a fresh hook and starts at level 1.
   Refreshing likewise discards the in-memory game. No localStorage,
   sessionStorage, cookie, or server session is used by the active hook.

Game engine contract (src/game/wordle.js)
-----------------------------------------
- Constructor input: optional numeric level, defaulting to 1.
- Constructor side effect: random selection from the locally imported
  dictionary through `selectWordByLevel(level)`.
- `isValidGuess(guess)` returns `{ valid: true }` or
  `{ valid: false, message }`. It trims and uppercases before checking exact
  length, ASCII A-Z only, and exact duplicate prior guesses.
- It does not check whether a guess is a real dictionary entry. Any distinct
  A-Z string of the right length can be submitted.
- `submitGuess(guess)` returns `{ success: false, message }` on validation
  failure. A valid guess returns `{ success, feedback, isCorrect, attempts,
  maxAttempts }`, appends the uppercase guess, and may change status.
- Feedback values are the configured strings `correct`, `misplaced`, and
  `unused`. The algorithm marks all exact matches first, then assigns at most
  one misplaced match for each remaining answer-letter occurrence. This
  matters for guesses containing repeated letters.
- `getState()` exposes the full selected answer along with normal game data;
  this is convenient for the UI but means it is not a secret-preserving API.
- `getHintData()` also returns the full answer plus definition, guesses, level,
  difficulty, and length for the client-side hint pipeline.
- The class does not reject calls to submitGuess after win/loss. The UI disables
  input after game over, but game-over enforcement is therefore primarily a
  UI constraint rather than an engine-level guard.

Word selection and level configuration
---------------------------------------
`src/config/gameConfig.js` and `src/game/wordSelector.js` each contain level
rules. They are separate mappings and can drift:

- gameConfig.js configures attempt limits and names for levels 1-12.
- wordSelector.js independently configures allowed word length and maximum
  dictionary difficulty for levels 1-12.
- For a level missing from the explicit selector mapping, the selector allows
  words of length 5 through 7 and difficulty 4 or below. The engine's attempt
  limit for a level missing from gameConfig falls back to level 1's setting.
- If a selected level produces no candidates, wordSelector.js warns and
  recursively selects at level 1. This changes the actual answer's length and
  difficulty from what the requested level might imply.
- Selection uses Math.random() over eligible dictionary records. There is no
  deterministic seed, weighting, repeat avoidance, or server-side selection.
- Dictionary file profile observed at this snapshot: 861 records; lengths:
  4 letters (7), 5 (317), 6 (455), 7 (63), 8 (17), 9 (1), and 10 (1);
  difficulty scores: 1 (67), 2 (468), 3 (279), and 4 (47). Since explicit
  levels 1-12 request lengths 5, 6, or 7, records of other lengths are not
  eligible at those levels. These counts are an inventory snapshot and should
  be recomputed if dictionary.json changes.
- The schema is informally expected to have word, definition, difficulty,
  length, and category. There is no runtime schema validation during import.

Hint request lifecycle and AI payload
-------------------------------------
1. Game.jsx offers a "Give me a hint" choice in the Hangman dialogue.
2. useWordle.requestHintWithChat() calls requestHint(), which checks the
   configured per-game maximum and cooldown. The current config allows three
   hints per game with a 30-second cooldown.
3. When allowed, requestHint() increments hint usage and records the timestamp
   before network success is known. Failed/errored AI calls still consume a
   hint and start the cooldown. Reset/level advance clears both.
4. The hook calls getHintContext(), which obtains Wordle.getHintData() and
   passes it to createHintContext(). That context includes the answer and
   definition as well as guesses, level, length, difficulty label, and
   configured game difficulty. It includes `attemptRemaining`, calculated as
   `6 - guesses.length`, irrespective of level-specific attempt limits.
5. aiService.getAIHint() expects a context with targetWord,
   targetDefinition, guesses, level, attemptsUsed, maxAttempts, and optional
   letter feedback arrays. The object produced by createHintContext() does
   not supply attemptsUsed or maxAttempts. As wired, attemptsUsed destructures
   to undefined; the service's attempt-mode comparisons consequently do not
   select the intended early/middle modes, and the prompt receives an undefined
   attempt value. The feedback arrays are not populated by the hook either.
6. The service sends two messages (system and user) with a model, token limit,
   and temperature. The system prompt includes instructions about not revealing
   the answer. The client sends the actual answer in the user prompt because
   the model needs it to produce a clue. Response handling takes the first
   line, strips simple surrounding quotes and a "Hint:" prefix, adds a period
   if absent, and checks basic length/placeholder format. This is not a
   content-safety classifier and does not reliably verify answer secrecy.
7. The hook appends the returned hint or a user-readable error to chatMessages.
   Game.jsx renders the latest AI message in the dialogue after the request
   completes. The separate HintChat component is not part of this active path.

Dialogue request lifecycle
--------------------------
- Game.jsx defines two dialogue choices: "Are you okay?" and "Give me a hint".
- The first calls dialogueService.generateDialogue() with the topic, tone, and
  token limit. dialogueService chooses a persona, creates system/user prompts,
  calls openrouterRequest(), and returns success/text/persona/model metadata
  or a failure message.
- The second uses the hint lifecycle above; it is not the dialogue service.
- The hint chat transcript is kept in useWordle hook state for the current
  level. Persona responses are kept separately in Game.jsx's local aiState.
  User interaction is constrained to preset choices; there is no free-text
  question input.
- A request in progress sets loading state and disables dialogue options.
  Errors are shown as response text; there is no retry/backoff policy.

AI request shapes
-----------------
Both services use a JSON chat-completions request with a `model` and `messages`
array of `{ role, content }` objects. The hint request also sets
`max_tokens: 100` and `temperature: 0.7`. Dialogue defaults to
`max_tokens: 80` and `temperature: 0.8`, with those values and tone/persona
selectable by the caller. The shared client POSTs JSON and parses a JSON
response; service code reads the first choice's message content.

The proxy accepts any JSON object at the named path and forwards the parsed
object rather than imposing a project-specific request schema. It does not
restrict which model, role, token limit, or message content a caller supplies.
The browser-side service uses only the response text it expects, although the
dialogue service also returns the raw provider response object to its caller.

AI transport and environment matrix
-----------------------------------
Relevant variable names (values are intentionally not reproduced here):

- `OPENROUTER_API_KEY`: server-side key read by server.js from process
  environment or a local .env file.
- `VITE_OPENROUTER_API_KEY`: client-side key read by openrouterClient.js for
  direct browser requests; the same name is also accepted as a fallback by
  server.js. Any VITE_ variable consumed by client code must be considered
  public in a client build.
- `VITE_OPENROUTER_MODEL`: optional model override; both AI services otherwise
  default to `gpt-4o-mini`.
- `VITE_USE_PROXY`: exact string `true` selects proxy mode. Vite development
  mode also selects proxy mode by default.
- `PORT`: optional server.js listen-port override; defaults to 4000.

Transport modes:

- Development default: frontend fetches same-origin `/api/openrouter` because
  `import.meta.env.DEV` is true. Vite listens on 3000; server.js listens on
  4000. The inspected Vite config has no proxy rule, so unless another
  deployment layer forwards that path, requests hit Vite rather than
  server.js. Starting `npm run proxy` alone does not bridge the ports.
- Production proxy mode: setting VITE_USE_PROXY to `true` keeps the browser
  request relative, but a hosting reverse proxy must route `/api/openrouter`
  to the separately deployed server.js process. That routing is not configured
  in this repository.
- Production direct mode: if proxy mode is off, the browser calls OpenRouter
  directly and uses a VITE_OPENROUTER_API_KEY value. This places the credential
  in a browser-accessible application and is not suitable for a confidential
  server secret.
- server.js replies with wildcard CORS headers, including for OPTIONS. It is a
  raw HTTP relay and does not restrict origins, authenticate callers, limit
  request size, apply quotas, or validate model/prompt fields before forwarding.
- The source contains two OpenRouter host forms: openrouterClient.js uses
  `https://api.openrouter.ai/v1/chat/completions` for direct calls, while
  server.js targets `https://openrouter.ai/v1/chat/completions`. Confirm the
  proxy target against the provider's current API documentation before release.
- Proxy-level HTTP failures are passed through as status and response text;
  thrown server-side errors are logged and returned as 502 JSON. The client
  throws for non-2xx responses and the higher-level AI services convert those
  failures to result objects.

Data inventory and confidentiality
----------------------------------
- Application data is static and embedded in the client build: the dictionary
  plus game rules and presentation strings.
- There is no user account identifier, server-side game record, database,
  storage retention policy, or application telemetry code in the inspected
  active path.
- AI network requests contain prompt text that includes the target word,
  definition, guesses, level, and related context. Dialogue requests contain
  preset topic text. These requests leave the browser and are sent to the
  configured OpenRouter endpoint, directly or through the local proxy.
- The app does not make a confidentiality guarantee for answers: the
  dictionary is downloaded as a client asset, the engine stores the selected
  answer client-side, and hook output includes the answer.
- The repository does not document user-facing disclosure, provider data
  retention settings, or a privacy policy. Those should be reviewed separately
  before public deployment.

UI inputs, outputs, and limitations
-----------------------------------
- GuessInput is the only active guess-entry component. It accepts letters
  A-Z, uppercases input, limits length, and submits on form submission. It has
  no dictionary-membership check, virtual keyboard, or explicit auto-focus.
- GameBoard renders submitted rows and all remaining blank rows; it does not
  show partial/in-progress letters because only full words are submitted.
- HangmanAI maps wrong guess count to a fixed set of seven visual descent
  records (0 through 6, clamped at the final record). The component receives
  maxAttempts for its progress percentage, but the visual state itself is
  clamped to the fixed array and is not derived from per-level attempt count.
- Game.jsx computes wrongGuesses as guesses.length, subtracting one when the
  current status is win. This prevents a winning guess from advancing the
  character; other accepted guesses, including wrong words, advance it.
- GameStatus renders text only. Retry and level advancement are managed by
  Game.jsx.
- Styling is split among uiTheme inline objects, global CSS, Tailwind classes
  used by HintChat/ChatMessage, and a generated layout string in GameLayout.
  The active Game page uses index.css classes rather than GameLayout.
- DialogChoiceBox is an overlay but is not implemented with a portal or
  explicit focus trap. Its backdrop closes on click. The close button title
  mentions ESC, but no keyboard escape handler is visible in this component.

Error and operational behavior
------------------------------
- Guess validation errors are returned as simple messages and do not throw.
- Word selection logs a warning and falls back to level 1 if no candidate
  exists.
- AI network/HTTP/response errors are caught by the hint and dialogue services
  and returned as failure-shaped objects; the hook displays error text in chat.
- The hint hook increments its counter before calling the external AI service,
  so temporary provider/proxy outages still use a hint.
- server.js attempts a local .env parse only if the process key is absent.
  If no key is found it warns at startup, but still starts listening; upstream
  requests then depend on the resulting authorization header being accepted.
- The proxy reads the full request body into memory before parsing; there is
  no explicit byte limit or request timeout in the inspected implementation.
- `scripts/testProxy.js` only reports the response and status; it does not
  assert configuration correctness, failure handling, security properties,
  or correctness of game logic.

Audit-oriented observations (source/documentation alignment)
------------------------------------------------------------
- Current runtime AI provider is OpenRouter. README.md, instructions.md,
  aiService.js comments, and Credits.jsx include old Groq/model references.
- The game takes whole-word guesses; documentation claiming letter-by-letter
  entry or a virtual keyboard does not describe GuessInput.jsx.
- The target word is present in frontend state and bundled dictionary data,
  and is included in the hint context sent from the browser. This architecture
  should not be treated as keeping answers confidential from the client.
- The OpenRouter proxy has wildcard CORS and no authentication or request-size
  controls in the current source. The dev client uses a relative API path, but
  Vite has no configured proxy to server.js.
- Hint safeguards are primarily prompt instructions and basic format checks;
  the source does not establish that generated text can never reveal an answer.
- README.md claims session persistence, but useWordle.js does not persist game
  state. Credits.jsx repeats this mismatch.
- No test framework, test files, lint script, or CI configuration appeared in
  the inspected project file inventory. scripts/testProxy.js is an ad hoc
  external-service request and does not test game rules.
- Some components and helpers are currently unused or overlap: AIDialogueBox
  and DialogChoiceBox, GameLayout, HazardDisplay, HintChat, wordList.js, and
  the formatter in hintService.js.
- Difficulty configuration is split between gameConfig.js and a separate
  level mapping in wordSelector.js. Changes to level rules should account for
  both.
